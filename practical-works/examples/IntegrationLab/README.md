# IntegrationLab — практическая работа № 13

Интеграция с внешним API через `HttpClient`: типизированный клиент, таймауты,
повторные запросы, размыкание цепи, идемпотентность и журналирование.
Решение сделано по методичке (`dotnet new sln -n IntegrationLab`).

## Структура

| Проект | Что содержит |
|--------|--------------|
| `src/PartnerApi` | партнёрский API: заказы в памяти, идемпотентность по `Idempotency-Key` |
| `src/IntegrationClient` | консольный клиент: `IPartnerClient` / `PartnerClient`, Polly-политики |
| `tests/IntegrationLab.Tests` | интеграционные тесты клиента (подмена транспорта) |

## Эндпоинты PartnerApi

| Метод | Адрес | Что делает |
|-------|-------|------------|
| `GET` | `/api/health` | проверка, что сервис жив |
| `GET` | `/api/orders` | список всех заказов |
| `GET` | `/api/orders/{id}` | заказ по идентификатору, 404 если не найден |
| `POST` | `/api/orders` | создаёт заказ; 400 без `Idempotency-Key` или при `Amount <= 0` |

Повторный `POST` с тем же `Idempotency-Key` возвращает уже созданный заказ, а не дубль.

## Устойчивость клиента

| Механизм | Где настроен |
|----------|--------------|
| Таймаут 5 секунд | `client.Timeout` |
| Повтор: 3 попытки с экспоненциальной задержкой для 408/429/5xx и сетевых ошибок | `GetRetryPolicy()` |
| Размыкание цепи: после 5 сбоев запросы не отправляются 30 секунд | `GetCircuitBreakerPolicy()` |
| Ключ идемпотентности | заголовок `Idempotency-Key` |
| Корреляция логов | заголовок `X-Correlation-Id` + логирование кода ответа и времени |

Клиент различает ошибки:

- **400** — ошибка клиента, повторять нельзя → логируется предупреждение, возвращается `null`;
- **404** — объект не найден → возвращается `null`;
- **429 и 503** — временные ошибки → их обрабатывает Polly (повтор), а после исчерпания попыток клиент возвращает `null` вместо падения.

## Запуск

```bash
# терминал 1 — партнёрский API
cd practical-works/examples/IntegrationLab
dotnet run --project src/PartnerApi --urls http://localhost:5100

# терминал 2 — клиент
dotnet run --project src/IntegrationClient
```

Клиент по шагам показывает: создание заказа, повтор с тем же ключом, список заказов,
обработку 400, обработку 404, повтор при 503 и запрос без ключа идемпотентности.

## Тесты

```bash
dotnet test
```

Тесты подменяют транспорт (`FakePartnerHandler`) и проверяют:

1. успешное создание заказа — 201, возвращается заказ;
2. повтор с тем же `Idempotency-Key` — возвращается тот же идентификатор;
3. чтение несуществующего заказа — 404, клиент возвращает `null`.

## Индивидуальное задание

| Требование | Где реализовано |
|------------|-----------------|
| Не менее двух операций: чтение и создание | `CreateOrderAsync`, `GetOrdersAsync`, `GetOrderAsync` |
| Типизированный HttpClient | `PartnerClient` + `AddHttpClient<IPartnerClient, PartnerClient>` |
| Таймаут, повтор, circuit breaker | `Program.cs`, `GetRetryPolicy`, `GetCircuitBreakerPolicy` |
| Ключ идемпотентности для создания | заголовок `Idempotency-Key`, хранилище `OrderStore.ByKey` |
| Обработка 400, 404, 429, 503 | метод `SendAsync` в `PartnerClient` |
| Логирование с корреляционным идентификатором | заголовок `X-Correlation-Id`, `ILogger` |
| Два интеграционных теста: успех и повтор | `tests/IntegrationLab.Tests/PartnerClientTests.cs` |

## Ответы на контрольные вопросы

1. **Почему нельзя `new HttpClient()` на каждый запрос?** Каждый экземпляр держит сокеты, при большом числе запросов они исчерпываются, а DNS-записи не обновляются.
2. **Что делает `IHttpClientFactory`?** Создаёт и переиспользует `HttpMessageHandler`, управляет временем жизни, позволяет подключать политики и DI.
3. **Какие ошибки временные?** 408, 429, 500, 502, 503, 504, таймауты и сбои сети.
4. **Повтор и размыкание цепи.** Retry повторяет запрос при временной ошибке. Circuit breaker после серии ошибок временно блокирует все запросы, чтобы не перегружать падающий сервис.
5. **Зачем ключ идемпотентности?** Сервер понимает, что повторный запрос — тот же самый, и возвращает существующий результат вместо создания дубля.
6. **Что будет без ключа?** Сервер не отличит повтор от нового запроса, возможен дубль.
7. **Как обработать 400 и 503 по-разному?** 400 — не повторять, вернуть пользователю ошибку; 503 — повторить с задержкой, это временная проблема.
8. **Зачем `CancellationToken`?** Позволяет отменить запрос при таймауте или отмене операции и освободить ресурсы.
9. **Как связать логи двух сервисов?** Передавать `X-Correlation-Id` и логировать его в обоих сервисах.
10. **Почему таймаут меньше общего времени операции?** Должен остаться запас на повторы и обработку ошибки.
