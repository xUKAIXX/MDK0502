# LibraryApp — практическая работа № 14

Данные, модели, DTO и репозитории: предметная модель, EF Core, отделение сущностей
хранения от DTO, репозиторий и проверка валидации через API. Решение сделано по методичке.

## Структура решения

| Проект | Что содержит |
|--------|--------------|
| `src/LibraryApp.Domain` | `Author`, `Book`, `Genre`, `Reader`, `DomainException` |
| `src/LibraryApp.Application` | DTO, `IBookRepository`, `IReaderRepository`, `BookService`, `ReaderService` |
| `src/LibraryApp.Infrastructure` | `AppDbContext`, конфигурации EF Core, репозитории, `DependencyInjection` |
| `src/LibraryApp.Api` | контроллеры, `Program.cs`, `appsettings.json`, Swagger |
| `tests/LibraryApp.Tests` | тесты бизнес-правил |

Домен не ссылается на EF Core и ASP.NET Core — это проверяется компилятором,
потому что слои разделены проектами.

## База данных

По методичке используется PostgreSQL; здесь подключена локальная SQLite,
чтобы проект запускался без установленного сервера. Схема создаётся при старте
(`EnsureCreated`), а чтобы построить её миграцией, выполните:

```bash
dotnet tool install --global dotnet-ef
dotnet ef migrations add InitialLibrary --project src/LibraryApp.Infrastructure --startup-project src/LibraryApp.Api
dotnet ef database update --project src/LibraryApp.Infrastructure --startup-project src/LibraryApp.Api
```

## Эндпоинты

| Метод | Адрес | Что делает |
|-------|-------|------------|
| `GET` | `/api/books` | список книг с автором и жанрами |
| `GET` | `/api/books/{id}` | книга, 404 если не найдена |
| `POST` | `/api/books` | создание книги; 400 при неверном годе или несуществующем авторе |
| `DELETE` | `/api/books/{id}` | удаление книги |
| `GET` | `/api/readers` | список читателей с книгами |
| `GET` | `/api/readers/{id}` | читатель, 404 если не найден |
| `POST` | `/api/readers` | создание читателя |
| `POST` | `/api/readers/{id}/books` | выдача книги читателю (связь «многие ко многим») |

## Запуск

```bash
cd practical-works/examples/LibraryApp
dotnet run --project src/LibraryApp.Api
```

Swagger — `http://localhost:5090/swagger`. База `library.db` создаётся и наполняется
демонстрационными данными автоматически (3 автора, 2 жанра, 3 книги, 2 читателя).

## Проверка валидации (по методичке)

1. Создание книги с корректными данными — **201**.
2. Неверный год (`Year = 1499`) — **400** с сообщением доменного исключения.
3. Несуществующий автор (`AuthorId = 999`) — **400** «Автор не найден.».
4. Список книг содержит автора и жанры — `GET /api/books`.
5. Удаление автора с книгами запрещено — `DeleteBehavior.Restrict` на связи.

| Требование | Где реализовано |
|------------|-----------------|
| Сущность «Читатель» и связь «многие ко многим» с книгами | `Reader`, `Book.Readers`, `Reader.Books`, таблица `book_readers` |

| Миграция и проверка схемы | команды `dotnet ef` выше, схема `readers`, `book_readers` |
| Два теста на бизнес-правила | `tests/LibraryApp.Tests/ReaderTests.cs`, `BookTests.cs` |

## Ответы на контрольные вопросы

1. **Сущность и DTO.** Сущность отражает предметную область и хранится в БД, DTO — форму передачи данных через API. Сущность не должна выходить наружу: иначе изменение схемы БД ломает контракт API.
2. **Зачем слой Domain.** Он содержит бизнес-правила и не зависит от инфраструктуры, поэтому правила можно проверять тестами без базы и легко переносить на другой стек.
3. **Агрегат и граница транзакции.** Агрегат — группа сущностей, которая сохраняется как единое целое; транзакция не должна переходить границу агрегата.
4. **Почему репозиторий не возвращает `IQueryable`.** Это утечка деталей EF Core: вызывающий код сможет строить запросы, которые нельзя проверить и которые могут выполняться неэффективно. Репозиторий возвращает готовые `IReadOnlyList`.
5. **Зачем `IEntityTypeConfiguration`.** Выносит настройку отображения в отдельный класс: таблицы, ключи, длины, индексы, связи — контекст остаётся чистым.
6. **Как EF Core находит конфигурации.** Через `modelBuilder.ApplyConfigurationsFromAssembly(...)` — он находит все реализации `IEntityTypeConfiguration<>` в сборке.
7. **`HasOne/WithMany` и `HasMany/WithMany`.** Первое — связь «один ко многим» с внешним ключом, второе — «многие ко многим» через промежуточную таблицу.
8. **Зачем `AsNoTracking`.** Отключает отслеживание изменений для чтения: меньше памяти и быстрее, если сущности не будут изменяться.
9. **Где валидировать входные данные.** Три уровня: атрибуты DTO (обязательность, длина, диапазон), бизнес-правила в сущности и ограничения БД (NOT NULL, UNIQUE, внешние ключи).
10. **Почему нельзя редактировать применённую миграцию.** Она уже выполнена в базах, и её повторный запуск даст другую схему; изменения оформляются новой миграцией.
