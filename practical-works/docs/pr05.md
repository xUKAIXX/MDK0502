# Практическая работа № 5. Web API: слои, DI, Swagger и конфигурация

**Вариант 3:** агентство недвижимости.

**Тема:** серверная часть на ASP.NET Core Web API: слои, внедрение зависимостей, Swagger, конфигурация.

**Цель:** разделить приложение на слои, настроить DI, вынести параметры в конфигурацию и подготовить интерактивную документацию API.

## Что сделано

- слои `Domain` → `Application` → `Infrastructure` → `Web`;
- Web API-контроллеры: `PropertiesApiController`, `DealsApiController`, `DictionariesApiController`, `AgentsApiController`;
- внедрение зависимостей через конструкторы;
- типизированные настройки `RealEstateOptions` через `IOptions<T>`;
- конфигурация в `appsettings.json` и переменных окружения;
- Swagger UI на `/swagger`;
- Polly-политики для внешнего API (retry + circuit breaker).

Ключевые файлы:

- `src/RealEstateAgency.Web/Controllers/Api/*.cs`
- `src/RealEstateAgency.Web/Program.cs`
- `src/RealEstateAgency.Application/Common/RealEstateOptions.cs`
- `src/RealEstateAgency.Infrastructure/DependencyInjection.cs`

## Ответы на контрольные вопросы

1. **Domain и EF Core.** Домен не должен зависеть от инфраструктуры: иначе бизнес-правила привязываются к провайдеру БД и их сложно тестировать.
2. **Слои проектами.** Компилятор проверяет направление зависимостей. В папках можно случайно импортировать что угодно.
3. **Порт и адаптер.** Порт — интерфейс в Application (например, `IPropertyRepository`). Адаптер — реализация в Infrastructure (например, `PropertyRepository`).
4. **`IClock`.** Абстрагирует время: в тестах можно подставить фиксированное время, а в production — `DateTime.UtcNow`.
5. **Времена жизни.** Singleton — один объект на приложение; Scoped — один на запрос; Transient — новый на каждое разрешение. DbContext обычно Scoped.
6. **DbContext как Singleton.** DbContext не потокобезопасен; параллельные запросы приведут к ошибкам и утечкам состояния.
7. **Выбор конструктора.** Контейнер выбирает конструктор с наибольшим числом параметров, которые он может разрешить. Можно явно указать `ActivatorUtilitiesConstructor`.
8. **Источники конфигурации.** `appsettings.json` → `appsettings.{Environment}.json` → user secrets → переменные среды → аргументы командной строки. Последний перекрывает предыдущие.
9. **`IOptions<T>`.** Даёт типизированный доступ, валидацию и обновление без перезапуска; `IConfiguration` возвращает строки и не типизирован.
10. **`ProducesResponseType`.** Описывает коды и типы ответов; Swagger показывает их в документации.
11. **Доменное исключение → 400.** Это ошибка входных данных или бизнес-правила, а не сбой сервера. Клиент может исправить запрос.
12. **Переход на EF Core и PostgreSQL.** Заменить in-memory репозиторий на EF Core, зарегистрировать DbContext и провайдер, добавить миграции; контроллеры и сервисы не меняются.

## Как проверить

1. Запустите приложение, откройте `/swagger`.
2. Проверьте `GET /api/properties`, `GET /api/properties/{id}`, `POST /api/properties`.
3. Измените `RealEstateAgency__MortgageApiBaseUrl` в переменной окружения и убедитесь, что настройка применяется.
4. Проверьте, что при отсутствии раздела настроек используются значения по умолчанию.
